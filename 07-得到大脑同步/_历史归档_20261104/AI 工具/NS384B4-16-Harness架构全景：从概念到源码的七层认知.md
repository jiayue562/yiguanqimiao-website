# Harness 架构全景：从概念到源码的七层认知

今天一天攒了 8 条 Harness 相关内容，从"是什么"到"怎么搭"到"源码级拆解"再到"跨领域同构"，几乎是一条完整的学习路径。按认知深度从浅到深排，一共七层。

---

## 第一层：概念——Harness 到底是什么

**一句话定义**：Agent = 大模型 + Harness。把 Agent 里的大模型拿掉，剩下的所有东西就是 Harness——规则、记忆、工具、思考-行动-检查的工作循环、上下文管理……全算。

Harness 不是某个具体文件或开关，它散落在 Agent 的各处，是和 Agent 融为一体的"灵魂"。它的唯一目的：**让大模型稳定、高效地为人类干活**。

核心判断：
- 模型有多强，决定了 Agent 的**能力上限**
- Harness 搭得好不好，决定了这些能力**能不能稳定发挥出来**

---

## 第二层：工程学——束导工程与都江堰类比

把 Harness Engineering 译为**束导工程**（约束 + 引导）。用都江堰做类比，一下就通了：

- 岷江 = 大模型（强大但野性难驯）
- 都江堰整个水利工程 = Agent
- 鱼嘴、金刚堤、飞沙堰、宝瓶口这些工事 = Harness

**束导工程四大支柱**：

| 束导工程支柱 | 都江堰对应 | 干什么用 |
|---|---|---|
| 分流分布 | 鱼嘴 + 金刚堤 + 离堆 | 把大任务拆成小任务，或拆成多个 Agent 协作 |
| 控量约束 | 宝瓶口 | 每一步输出、最终成果都要满足要求才能放行 |
| 兜底机制 | 飞沙堰 | 死循环、异常时降级、超时拦截、自我修复，多余能量泄洪 |
| 成长维护 | 岁修制度 | 根据模型能力变化、业务需求变化持续迭代维护，才能千年不废 |

飞沙堰的智慧尤其值得琢磨：它不是主动"拦截"，而是被动"引导"——高度严格控制在卧铁之上两米，水位超过临界点就自动溢流，同时利用弯道环流原理甩走 80% 的泥沙。**最好的兜底机制不是筑起高墙，而是设计一个恰到好处的溢出口。**

而都江堰真正的"微内核"不是鱼嘴或飞沙堰，是那个不起眼的**岁修制度**——"深淘滩，低作堰"六个字，两千年持续维护，才让工程活到今天。 一个能持续运转的系统，不是因为它永不损坏，而是因为它有定期自我修复的机制。

## 第三层：产品形态——DeepSeek Harness 怎么做的

**核心理念：一切皆插件**

- 微内核架构，连 loop、plan mode、Go 这些最基础的能力全都是插件
- 好处：配置层自由组合，不用改源代码，加几个配置文件或用 SDK 就能拼出新东西
- 每次运行有"轨迹"可查——每一步用了什么 prompt、调了哪些工具、thinking 过程是什么，全部透明

**四种工作模式**：
1. **标准模式**：工具完备（Shell、文件编辑、网页检索等）
2. **PTC 模式**：通过 TypeScript 代码做多步工具调用，擅长编码、自主运行时间长
3. **极简模式**：只保留 Shell 和文件编辑，环境干净
4. **创造模式**：可以用自然语言直接定制新的 Agent preset 和插件——最有想象力的一个

## 第四层：源码架构——Agent 版的 Spring

翻完源码才发现，DeepSeek Harness 真正想做的根本不是一个固定的 Agent，而是一套组装 Agent 的系统。它背后的架构思想跟 Spring 简直一模一样。

**核心三问**：

### 1. 插件插在哪里？

在 core 包里——这是 Harness 的核心容器。容器里分门别类设好了多个接入点：

- **scope**：上下文元语（不使用 ctx key）
- **session**：存储会话日志和内存
- **system prompt**：系统提示词，每次对话一起发给大模型
- **tools**：工具函数
- **agent**：封装和大模型交互的方式（提问、流式输出）
- **agent loop**：Agent 驱动器（重试、循环逻辑）

不是什么都能往里插——只有和 Agent 相关的东西才接收。容器就像 Spring 的 IOC 容器，分门别类装着不同类型的 Bean。

### 2. 插件怎么插进去的？

通过 `register` 注册方法，往容器的 `layer.tools` 里注入一个 `Tool Definition`。而 `NamedEntries` 本质上就是一个 **Map**——key 是工具名，value 是 Tool Definition。

有没有想到 Spring？Spring 里装 Bean 的也是一个 Map，里面放的是 **Bean Definition**。Harness 放的是 **Tool Definition**。名字不一样，结构完全一样。

更妙的是联动注入：一个 FS 文件系统插件，激活时会同时往 **system prompt**（告诉大模型有这个工具、怎么用、优先用它而不是 shell 指令）和 **tools**（实际执行函数）两个接入点注入。 加一个插件不是加一个孤立功能，是同时改变了 Agent 的"认知"和"行动"。

### 3. 插件怎么拿出来用？

通过 **agent presets（运行模式配置文件）**。

每个 preset 就是一个 yaml 配置文件，里面列了要加载哪些组件、每个组件的参数是什么。这就相当于 Spring 的 `application.yml`——要用哪些 Bean，配置文件里写好就行。

preset 划定的是 Agent 的**能力边界**——在这个边界之内，具体用哪些工具、怎么用，由大模型来判断。边界由人定，执行由模型定——这是 Harness 设计里非常精髓的一个分层。

而且它支持**热更新**：改配置文件不用重启应用，新建一个 preset 立刻就能用，插件可以动态启用/停用。 这是传统 Spring 做不到的——基于 TypeScript 的语言特性，Harness 把"配置即运行"做到了极致。

## 第五层：应用方向——工作台、插件生态、企业定制

### BI 工作台：Harness 嵌信息系统，不是反过来

未来的工作界面应该是 **Harness 嵌信息系统**，而不是信息系统右下角加个聊天窗。聊着聊着界面就变了，数据看板实时跟着对话更新。

更深一层：人盯数据是少数情况，**未来一定是 Agent 去盯数据**——专门的会话盯利润率、盯中部数据，触发阈值就自动发消息、自动处理。工作台慢慢接管手头工作，人去干更有价值的事。

### 插件生态：好架构降低定制门槛

用创造模式的对话方式就能做出侧边栏聊天插件（热启动→封装成真正的 plugin→分享）。好的架构能大幅降低 harness 定制门槛，GitHub 上很快会出现大量插件市场。

低代码会被淘汰，但**好架构依然重要**。

### 企业落地：定制化 Harness 是大机会

企业不满足于现成的通用产品，定制化 harness 需求会非常旺盛。围绕同一套架构标准生产插件、互相协同流转，市场会很快欣欣向荣。

---

## 第六层：跨领域同构——Harness 与东方哲学的七个对应

Harness 架构不是孤立的技术发明，它和你书里那套"一心三界五行九层"的母结构是**同一个模子**。七个对应点：

| Harness 架构 | 对应理论 | 所在书 |
|---|---|---|
| Agent = 大模型 + Harness | 人 = 心 + 五行 + 身 | 五行人格心理学 |
| agent / prompt / tools 三层接入点 | 灵 / 心 / 身 三层结构 | 心文化 / AI原生组织 |
| core 容器（IOC） | 心文化之"体"，体用不二 | 心文化 |
| 插件联动注入（prompt + tool 一起注入） | 五行生克，能量联动网络 | 五行人格心理学 |
| agent presets（运行模式配置） | 立象尽意，象思维四步法 | 象与模 |
| 热更新 / 动态插件 / 持续演化 | 生生自化，数据飞轮 | 生生·文化操作系统 / AI原生组织 |
| Tool Definition（描述而非硬编码） | 五色光逆修，以行修心 | 五行人格心理学 |

甚至中药方剂的"君臣佐使"也是同一个结构：君药是主插件，臣药是辅助插件，佐药是反调插件，使药是路由插件。同一味药在不同方子里角色不同——和同一个插件在不同 preset 里权重不同，是同一件事。

三十亿年前，噬菌体就发明了"一切皆插件"——换一个尾刺蛋白，就能突破细菌的新防线。 插件架构不是什么新东西，它是生命演化最古老的策略之一。

---

## 第七层：一句话收束

大模型是岷江，能力已经够强了。接下来真正决定 AI 生产力能不能落地的，不是模型再大几号，而是我们能不能像李冰修都江堰那样，把 Harness（束导工程）搭好——分流、控量、兜底、岁修，让这股强大的力量稳定地流向该去的地方。

而 DeepSeek Harness 用源码证明了一件事：这套束导工程的最佳架构，就是**微内核 + 插件化 + 配置驱动 + 热更新**——它不仅是 Agent 工程的最佳实践，也是一个从都江堰到噬菌体、从中医方剂到组织设计，跨越两千年、横跨多个领域的通用结构。
