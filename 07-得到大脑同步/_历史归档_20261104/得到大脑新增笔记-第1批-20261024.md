## 01 知识库两套用法：自己用的和给别人用的

- `note_id`: 1925007272308938448
- 所属库：AI 工具（JlW5Q9B0）｜类型：plain_text｜创建：2026-10-24 08:45:29
- 原文：https://www.biji.com/note/1925007272308938448
- **判定：D 类（版权待定）** —— 主体内容为外部产品（`newtype.os` / `newtype.pro` / newtype MCP）实践，非本机自有成果

2024 年我出过一堆搭知识库的视频，向量数据库、RAG 都聊过，很多人是因为知识库才认识我、加入星球的。两年过去，我现在怎么用？分两类：自己用的，给别人用的。

先说自己的。有一条从头到尾没变：资料得在自己手里。换模型、换 Agent，积累都还在，不用从头再来。

变的是做法。我不再搭传统 RAG 了，模型上下文窗口大了，能一次放更多原文。但长上下文不是万能的：资料真的多到装不下，或者你想压低输入成本，还是得靠检索。而且技术上，装得下不等于模型在这么多内容里保持同样的精度。

所以我做了两件事。

第一，用 Obsidian 的原生检索。它的精确检索一直被低估，不是单纯关键词匹配，而是把关键词、笔记结构、标签、属性组合起来查，精度高得多。怎么让 Agent 用上？官方出了 CLI，让 Agent 配好，告诉它以后查资料优先走 Obsidian CLI。

第二，建 Wiki。检索再好，库是一团糟也白搭。我建了一套 Wiki，结构化地呈现知识库里有什么：反复出现的概念、主题是哪些。它不只是目录，还把我过去讨论过的观点和它们之间的关系整理出来。整理过的东西，Agent 不用每次从头再来。有新内容还能继续更新，让它长。对 Agent 来说，Wiki 就是一张地图：这个库是干嘛的、有哪些已经整理好的、要原文去哪找。

这套我在 newtype.os 里早就实现了，用了挺久，效果不错。

再说给别人用的。我在 newtype.pro 上发了所有帖子、文章、视频脚本和课程，但那是给人看的。用户想把我的内容喂给 Agent 参考怎么办？我把网站内容整理成了一个知识库，用了两个技术：RAG 和 MCP。

RAG 这边，文字内容切块、建向量索引，模型靠语义找最接近的内容；同时网站也做关键词匹配，两条路一起找。接入用 MCP，newtype MCP 提供搜索内容、读取原文、浏览目录这些能力，会员给自己的 Agent 装上就能调用。以前这些内容主要是给你看的，现在它们也能进你的工作流帮你做事。

总结一句：选什么方法，看资料放在哪、谁来用、Agent 怎么找到并读懂它。方法可以变，但自己的积累要留在自己手里，还要能持续发挥作用。

## 02 深度思考：把「模糊变可接手」补上接口

- `note_id`: 1924808115749057568
- 所属库：AI 工具（JlW5Q9B0）｜类型：plain_text｜创建：2026-10-22 05:14:10
- 原文：https://www.biji.com/note/1924808115749057568
- **判定：B 类** —— 通篇第二人称对话体 + 结尾「## 我不确定的」模板，属 AI「发芽」输出，非悟空成品

## 这条线真正的名字是「接口」，不是「转化」

你写的动作是「把模糊的东西变成可以接手的东西」。这句话里藏着两个不同的活：**转化**（把模糊变成清楚）和**接手**（让另一个人或另一个系统能接着干）。你七段帖子里的成功案例，全是后者——网关挡差异、Skill 定边界、微信摸平台的门。而失败风险全在前者：**你默认模糊可以被问清楚。**

Karpo 那条数据真正扎的地方在这：70%–80% 的 query 是模糊的，不是因为用户懒，是因为**意图还没成形**。没成形的东西问不出来，只能给出来。所以「一次问一个问题」这条设计原则，前提是错的——它假设用户答得出来。

## 你可能没想到的三处

### 一、滑杆和三个方案，不是同一类接口

VibePad 那种四象限滑杆，摇的是**状态**（我现在什么感觉）；给三个具体方案让他挑，挑的是**路径**（我往哪走）。状态可以摇出来，路径摇不出来。

你的单人测评、关系测评，用户进来时其实两样都缺：既说不清自己什么状态，也选不出想要什么路径。**所以该先给状态入口，再给路径入口**——先让他摇出「我最近是这种」，再从那个状态里长出三个选项。反过来先给三个方案，他只会挑最像标准答案的那个，测出来的东西是假的。

### 二、你的产品本身就是一台 VibePad

这一点你自己可能没看见：**五行分型就是滑杆。** 用户说不清自己，你给他五个维度让他对号——这跟四象限滑杆是同一个动作，只是你把滑杆做成了文化形态。

那么 Karpo 的经验对你就不是「可以借鉴」，是「你已经做对了一半，但用错了地方」：你把滑杆用在了**测评里**（用户已经打算做测评的时候），却没用在了**入口处**（用户还不知道自己要什么的时候）。三个 Skill 缺的那一段，你的产品里早就有现成的零件。

### 三、Delegation Rate 对你自己比对客户更狠

你拿它量味藏团队「愿意把多少件事真正交给 AI 办」。但你自己呢——一百二十多篇笔记、知识库、跑顺的方法，这些都是**你不敢委托出去的东西**。你宁可自己写，因为写的过程就是你想的过程。

这不是毛病，是判断：**认知类的活，委托率天然低，因为委托出去省的是时间，丢的是判断力。** 所以 Delegation Rate 不能当通用指标用，它只对「执行类任务」有效。把它套到「想清楚一件事」上，会得出一个荒谬的结论：越想清楚的人，越不合格。

## 第四节那个毛病，比你自己写的更严重一层

你识别出「把自己已有的能力当成别人态度上的问题」。这个自省很准，但你只把它当成**表达问题**（话说重了）。它其实是**产品问题**：

你的一百二十多篇笔记，是你的**私有上下文**。用户没有。所以你那句「这个过程并不难」，不是语气问题，是你把一个需要 120 篇笔记才能跑通的动作，当成了一步就能做的事。

**检验办法升级一版**：不看对方能不能照着做，看**他手上有没有你做这件事时用的那份材料**。没有，就不是他不行，是你的交付里缺了那一块。

## 往下走：三个动作，按顺序

1. **先做状态入口，不做方案入口。** 给「还没想清楚」那一段加一组滑杆（三到四维，摇完给一句判词），别急着给三个方案。
2. **把 Delegation Rate 拆成两个指标。** 执行类任务看委托率，认知类任务看「委托后返工率」——返工率高说明这段还不能交出去，跟你愿不愿意没关系。
3. **给每个 Skill 配一份「最小上下文清单」。** 写清它假设用户手上已经有什么。这份清单就是你说的「检验办法」的落地版——用户缺哪一条，Skill 就在那一步先补，而不是先问。

## 我不确定的

- Karpo 的 70%–80% 这个数，我只从你的转述里看到，没核过原始出处，当方向用可以，别当基准写进方法论。
- 「先状态后路径」这个顺序，是我从滑杆和选项的性质推出来的，没有实测。它值一次小样本验证：同一批用户，一半先摇滑杆一半先看方案，看哪种后续追问更少。

# 从一个做法到一套判断：今天这几段帖子背后的同一条线

今天发的几段话看着散：三个 Skill 的分工、三个 Agent 的镜子、站在产品层面看 AI 工具、模型网关、搞钱社群、微信 Agent 生态、Agent 的两个方向。整理下来，它们其实是同一条线在七个位置上的切面。

## 一、这条线是什么

**所有问题都归结到同一个动作：把模糊的东西变成可以接手的东西。**

- 三个 Skill 分的是「想法有多模糊」：还没想清楚 / 有选项拿不定 / 要一个有依据的判断
- 三面镜子分的是「一个人身上有三种声音」：理性的、心里的、没看见的
- Karpo 讲的是「用户开口之前那一段」：意图还没成形时怎么接住
- 微信那件事讲的是「平台的边界在哪」：哪些门是开的，哪些门一碰就关
- 产品层面看工具讲的是「什么该抓重点」：架构、修得动、还是小毛病
- 网关讲的是「把差异挡在哪一层」：模型可换，接口不能跟着换
- 搞钱社群讲的是「快和慢的代价」：追热点是没别的可讲，长期是有东西可讲

七个位置，一个动作。

## 二、三处最该记住的判断

**第一处：模糊不等于没有偏好，只是说不出来。**
Karpo 的数据：用户 query 里 70%–80% 都偏模糊，有人上来只打一个词「Food」，或者「我女朋友不理我」。她们做了个 VibePad，四象限滑杆，让用户摇出想要的状态——因为很多人不是有表达压力，是真的不知道该怎么把感觉说出来。这条直接改了三个 Skill 的设计前提：一次问一个问题，前提是用户答得出来。给选项、给滑杆、给具体方案让他挑，比追问有效。

**第二处：「代替人」和「代理人」不是分类，是划战场。**
Karpo 创始人 Leah 的原话逻辑：代替人的核心生产要素是智力，模型公司掌握了生产智力的方式，所以那大概率是模型厂商的机会；代理人的生产要素不止智力，还包括贴近场景、交互、品牌气质、线下供给，要素更杂，创业公司才有灵巧的身位。拿它当分类标签，就丢了它最锋利的部分——它说的是「哪块地你争不到，哪块地你能争」。

**第三处：核心指标是 Delegation Rate，不是 DAU。**
用户愿意把多少任务真正委托出去。这个尺子比满意度硬，因为它量的不是喜欢，是敢不敢交。放到味藏身上同样成立：团队愿意把多少件事真正交给 AI 办，而不是让 AI 出稿自己再改一遍。

## 三、和 AI 原生组织那条线的接口

- **曾鸣说组织基本单元从岗位换成任务**，Karpo 说未来淘宝、京东、DoorDash 这些平台可能都不直接面向用户，面向的全是 AI，供给侧会想「怎么让 AI 选中我」，To C 大厂会想「怎么成为那个入口」，甚至可能出现面向 Agent 的竞价广告。这是同一个结构变化的两端：一端是组织内部按任务重组，一端是市场外部按意图重组。
- **陈春花讲智能孤岛**：财务智能体生成预测报表却无法触发销售策略调整，营销智能体捕捉到需求信号却不能驱动供应链排产，所有信息仍需通过人的会议、邮件、表格转译——人类依然是低速、脆弱的「中心路由器」[[70105d94]]。这跟曾鸣的「旧组织是认知压缩结构」是同一句话的两种说法。
- **网关和本体是同一个道理的两层**：网关管调用层的可替换，本体管语义层的可替换。模型可以随时换 GPT、Claude 或开源模型，但企业本体的积累——对象定义、业务规则、Action 映射、安全策略——是经年累月沉淀下来的领域知识，模型是可替换的，本体不是[[733b34f2]]。
- **Delegation Rate 和 AI 原生组织的四阶段能对上**：S1 工具普及期是「人带助手」，S4 治理进化期是「人领导、Agent 运营」[[1a2b3f0f]]。从 S1 走到 S4，量的就是委托率。

## 四、一处需要自己警惕的地方

今天这几段里，有两处是同一个毛病：**把自己已经有的能力，当成了别人态度上的问题。**

- 「这个过程并不难」——对你不难，是因为你有一百二十多篇笔记、有知识库、有跑顺的方法
- 「站在产品层面看，就能抓住重点」——你能绕开小毛病，是因为你是产品人；普通用户绕不过去

这个毛病在做 Skill、写方法论、卖产品时都会重复出现。检验办法很简单：把这句话说给一个没有你那套底子的人听，看他能不能照着做。做不到，问题就在这句话里，不在他。

## 五、可以往下走的一步

三个 Skill 现在缺的正好是 Karpo 补上的那一段：**用户说不出自己想要什么的时候，怎么办。**

下一步可以试：给「还没想清楚」这一段加一个不靠提问的入口——三个具体方案让他挑，或者一组滑杆让他摇。看哪个更接得住。

这个改动很小，但它是从「问」到「给」的转向，值得单独试一次。

## 04 深度思考：AI原生组织的三个断点

- `note_id`: 1924873707416355168
- 所属库：AI 原生组织（J8x2ywvJ）｜类型：plain_text｜创建：2026-10-22 22:12:17
- 原文：https://www.biji.com/note/1924873707416355168
- **判定：B 类** —— 同模板（第二人称 + 「## 我不确定的」），且含味藏内部业务细节

## 一句话结论

曾鸣的 AI 原生组织是一张**为「任务可拆、结果可验」的组织画的底图**。餐饮是任务高度耦合、结果无法切分的组织。这张底图在味藏身上，会断在三个地方：任务切不开、结果验不了、认知收不上来。这三个断点，就是书稿真正值钱的部分。

## 一、他的底图，四层骨架

- **基本单元**：岗位 → 任务单元。先定义问题，再拆任务，明确 DRI，围绕结果组织人、Agent、Skill、工作流、数据和反馈。
- **人的定义**：知识工作者 → 创智人才。高能动性（自己定义问题）+ 超强学习能力（从第一性原理重构问题）。
- **协作方向**：Agent 调用人，而不是人用 Agent。区别只在一处——人的判断有没有回到 Agent 的学习闭环。
- **运转底座**：组织OS 四件套——组织记忆、AI学习、反馈进化、技术底座。核心原则是 Context, not Control。

底层一条主线：**Learning Loop**。个人、团队、组织、业务，四层都要闭环。竞争优势从「执行力×人数」变成「学习循环转一圈要多久」。

## 二、断点一：任务切不开

曾鸣的模型隐含一个前提：任务可以被切分成「端到端、可交付、可验证」的单元。这在他举的例子——研发、编程、AI 短剧——里成立。

餐饮不成立。一家门店的营业额是店长、料理长、前厅经理、厨师、服务员十几个人一起干出来的，很难切清谁交付了什么。你在三块拼图那条笔记里已经点到这一层：曾鸣的模型为「任务可拆」设计，餐饮是「任务高度耦合」的组织。

但味藏已经给出了自己的解法，而且比曾鸣更具体：**用招牌菜当切分器**。18 道招牌菜一出来，一个任务同时挂住三个人——料理长管出餐标准、店长管客群结构、前厅经理管仪式和氛围。任务不是被拆成三份，而是被同一个对象串起来，三个人各自对同一个结果的不同侧面负责。

这是对「任务单元」的一次改写：**任务单元不一定是可拆的，也可以是被一个共同对象锚住的。** 这句话可以成为书稿里的一节。

## 三、断点二：结果验不了

曾鸣说「反馈与进化：新洞见新决策经真实结果验证」。这句话在业务里成立，在组织判断里不成立。

「这个中层该不该留」「这个仪式该不该砍」「这个创业单元该不该独立」——这些事三年后才见分晓，甚至永远见不了分晓。没有结果，就没有验证；没有验证，学习闭环会空转，而且表面看起来一切正常。这大概也是他说「目前还没有看到完整成熟的组织OS案例」的真正原因：不是技术没到位，是**判断的验证标准没到位**。

味藏这里已经有一手很硬的答案：**把年度计划拆成三类**。存量门店按峰值定数（金二 150 万是座位数决定的恒定量，不是计划）；增量创业单元做季度滚动预测；只有新开店这种大额投入才做年度计划。你追到 1860 年代英国预算制度那条线，说明年度计划从出生起基因里写的是支出上限，不是增长目标。

这套拆分，本质是**给不同确定性的任务配不同的验证周期**。这比曾鸣的「真实结果验证」更可操作：不是所有判断都等结果，而是先分清这件事的结果多久能看见。

## 四、断点三：认知收不上来

组织OS 第一步是组织记忆：把事实、判断、分歧、历史决策及来源沉淀下来。曾鸣说「为什么现在很多人愿意把讨论录下来」——因为讨论过程本身包含决策背景。

味藏已经在做这件事，而且做得比大多数公司实在：这几天的组织架构会、战略会、年度计划讨论会，全部录了音、转成了笔记。这就是组织记忆的原始素材。

但真正的问题在第二步：**AI 学习**。曾鸣说 AI 要能从不同人的思考决策里学习，像新参与者一样提出观察。这要求的不只是录音，而是录音里那些「谁不同意谁、为什么最后改了主意」的分歧被结构化出来。

味藏有一个天然优势：会议里那些「抢答罚款 1000 元」「不许话密」的规则，本质上是在**保护慢思考**。这恰好是 AI 学习最需要的东西——不是结论，是推理过程。你那条「真正的战略共识是推理方式的共识」，在这里落地了。

## 五、全网补的三块

- **验证成了新瓶颈**。清华李宁的判断：AI 让「生成」变便宜之后，组织瓶颈从生成转向验证，分工逻辑从按工作量切分转向按认知带宽切分。这直接支撑了断点二。
- **中层不是消失，是换岗**。多数材料说中层在蒸发（信息中转、进度汇总被接管），但《哈佛商业评论》那一路的观点是：中层未来的核心价值是把战略意图转化为可执行行动。曾鸣自己也留了口子——人才成长、能力建设、关键判断、利益协调仍然重要。所以准确说法是：**中层的「传声」功能死了，「判断」功能升值了**。
- **Agent 开始有工号了**。今年 8 月，张江上线了智能体身份码平台，30 家单位参与。Agent 一旦有了身份，第一个问题不是「它能干什么」，而是「谁给它派活、谁验收、出事谁担责」。这正好接上曾鸣说的「重新设计权责、权限与协作机制」。

## 六、一个你可能没想到的角度

曾鸣把「Agent 调用人」讲成效率问题——让人判断回到学习闭环。但反过来看：**人的知识被抽走一次，这个人就贬值一次**。他的价值从「我会做」变成「我贡献过一次判断」，然后被沉淀进组织记忆。

所以创智人才那两个特征，其实是一条生存线：你必须跑得比自己知识被抽走的速度更快。落到味藏，店长和厨师长如果只是「会做」，在这套系统里是耗材；能不断定义新问题的人，才是资产。

## 七、落到味藏的三步

1. **把 18 道招牌菜写成「任务锚点卡」**：一道菜挂三个角色、各自对什么结果负责、多久能验证一次。这是断点一的解法，也是组织架构图之外的第二张图。
2. **给组织判断造替代验证标准**：凡是三个月内看不到结果的判断，必须写明「我们赌的是什么、什么信号出现说明赌错了」。这是断点二的解法。
3. **把会议录音变成分歧库**：不只记录结论，专门标出「谁不同意、理由是什么、最后怎么改的」。这是断点三的解法，也是组织OS 的第一步真功夫。

## 八、我不确定的

- 曾鸣说 2027—2028 年原生产品密集涌现。这个判断没有可证伪的验证标准，如果要在书稿里引用，最好自己补一句「什么信号出现算他对了」。
- 「招牌菜当切分器」这套，在味藏跑得通，但能不能推广到别的餐饮企业，取决于招牌菜体系是否足够稳定。这一点需要更多样本。
- 组织记忆的边界：录得越全，权限和隐私问题越大。曾鸣提了一句「透明需要与信息机制、职责、技术设计配套」，但没给方法。这块目前是空白，也是可以写的地方。

# 组织的树突：从神经元的灵活决策机制看 AI 原生组织的四层结构

## 种子

中科院脑智卓越中心徐宁龙团队 2026 年 10 月在《科学》发表的研究，第一次用实验证明：灵活决策不需要重塑突触，改的是顶端树突送下来的推断信号，和胞体送上来的感觉输入在同一个细胞里现场比对。

这条机制往组织上一放，正好回答了味藏最近一直在问的那个问题——规则变了，是重训整个组织，还是留一个区室专门装规则。

## 一、机制本身：把「学到的」和「正在判断的」分开存

实验设计很干净。小鼠听不同频率的声音，判断比当前边界高还是低，边界在无预警的情况下变，小鼠只能从奖励反馈里反推规则。研究者同步记录第 5 层端脑外投射神经元的顶端树突和胞体，看到的分工是：顶端树突主要编码推断出来的抽象规则，胞体更多表征感觉信息，而跟选择相关的输出信号在两个区室都出现了。

最关键的是因果那一步：用光遗传学选择性抑制树突活动，胞体的选择信号显著减弱。前面看到的都是相关，这一步才叫因果。

它推翻的是一百多年来的一个简化：神经元被当成一个均质的「点」，只做加权求和。这个模型解释不了灵活决策，因为如果每换一套规则都要重塑突触，能耗和训练量都撑不住。新解释是——规则不用存在突触里，可以存在同一个细胞的树突区室里，按需和感觉输入现场比对。

一句话：把「学会的」和「正在判断的」分开存，前者贵、后者便宜。

## 二、四层对应

### 突触层：制度、标准、SOP

这一层最贵，改一次要全员重训、重新磨合，还伤士气。味藏那 18 道招牌菜的口味标准、食材调性，就是突触。这类东西不该随规则变化而改，改了就是灾难。

味藏会议里已经把这个定位说清楚了：企业的制度规则对应国家法治，罚款是维护制度底线的手段，规则是底线，文化是上层追求，没有底线规则，企业文化无法建立。制度这一层就该稳，稳才便宜。

### 树突层：当前规则 + 上下文

这一层便宜、可快速切换。曾鸣说的「给上下文，而非控制」，本质上就是在组织里造一个树突区室：把背景、意图、当前约束给足，让一线自己现场比对，而不是等审批。

味藏现在缺的恰恰是这一层。7 层架构里，战略层、决策层、指挥层、赋能层、后勤层、门店执行层、数据层都画出来了，但「当前规则是什么、这周变了什么、为什么变」这套东西，还没有专门的载体。规则只写在制度里，就只能靠改制度来改规则——这正是最贵的路。

### 胞体层：一线的感觉输入

门店客流、老客户流失、厨师队伍状态。这一层本该是事实，但在很多组织里，事实要先经过层层汇报才到决策者手上，等到了已经变形。

味藏会议里说「组织架构需要设置数据层，包含数据审核和数据回流，管理层基于回流数据做决策」，这就是在修胞体的输入通道。你们还提了一个更狠的判断：之前的数据闭环不是实时的，现在这套实现了实时回流。实时与否，决定的正是胞体信号到决策层时还是不是原样。

### 第四层：比对必须在同一个地方发生

神经元最厉害的地方不是树突能存规则，是规则和感觉在同一个细胞里当场对账。

放到组织里：判断「这条规则在这个门店还成立吗」的人，必须同时拿得到规则和现场事实。如果规则在总部、事实在门店，中间隔三层汇报，那就不是比对，是传话。

这解释了为什么科层制在变化快的环境里必死——不是层级太多，是对账被拆散了。

味藏那个「AI 原生平台 → 赋能层 → 执行层 → 数据回流 → AI 组织」的循环，本质上就是在造这个对账场所。它成立的条件只有一个：回流的数据必须保真。会议里董事长提的那个疑问很准——「我们会不会在等待实时出现？」如果数据回流了但没人当场比对，那实时只是更快地看见问题，不是更快地判断。

## 三、这个机制顺手解释的两件事

**第一件，为什么巡检会流于形式。** 会议里说月度巡检「久而久之就变成一个走流程的事情」，预警后还是走流程。用这个机制看很清楚：巡检原本是树突上的一条临时推断——「这个月该看这几项」。它被固化成制度之后，就再也接收不到现场反馈了。突触化本身没错，错的是在还在变的环境里用固化的规则。

**第二件，为什么「仪式泡软组织」。** 仪式就是被写死在突触里的东西，而它原本该是树突上的一条临时推断。当一个临时规则被固化成制度，它就再也接收不到现场反馈了。

## 四、边界：别把类比推到底

神经元这套机制是亿万年演化出来的，前提是能量极度受限、每次重训代价极高。组织不完全一样：组织改制度的成本比大脑改突触低得多，而且组织有语言、有文档，可以外置记忆。

所以类比推到「该稳的稳、该活的活、对账要在同一处」就够了。再往前推就成了硬套。

还有一个必须说清的：这篇论文证明的是「树突参与认知计算」，不是「单个神经元等于一台完整计算机」。报道里那句「单个神经元本身就是一台小型计算机」是比喻，论文说的是树突计算参与。类比到组织时，也别把「一个细胞能算」推成「一个超级个体能包办一切」。

## 五、下一步

按这个框架，味藏眼下缺的不是架构图，是树突层。具体动作可以很小：给现有的日汇报加一格——「今天哪条规则我判断不适用了，为什么」。这一格不进制度、不进考核，只进上下文。跑一个月，看有多少条被反复提到，那些才是该固化成制度的。

这一步不用等架构定稿，明天就能加。

## 种子引子

这篇的起点是一篇神经科学论文，落点是味藏的组织架构。真正值得带走的不是「神经元像组织」这个比喻，而是那句：规则和事实，必须在同一个地方对账。架构图画得再漂亮，只要对账被拆散在三层汇报里，它就还是一台为稳定而生的机器。
