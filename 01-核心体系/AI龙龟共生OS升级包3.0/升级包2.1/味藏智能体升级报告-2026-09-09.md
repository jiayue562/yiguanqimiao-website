## 一、先说真问题

我没按字面去"加功能"，而是先查了一件事：**大库里的东西，味藏智能体吃进去没有。**

### 查出来的三处硬伤

|---|---|

**一句话诊断：叶子很肥，根是空的。**

## 五、这次的坑（写成疫苗）

1. **IMA 目录树不能只按深度递归遍历**——深层目录会漏。正确做法是**按 folder_id 逐个全量拉取**（本次深度 3 只拿到 1008 份，改按 ID 拉取后是 **4916 份**，差了 4 倍）。
2. ⚠️ **IMA 配额是「总 API 调用次数」，不是「正文篇数」**——**列目录同样计次**（`get_knowledge_list` 也会撞 `220021`）。全量遍历 322 个文件夹 ≈ 320+ 次请求，抓 1 份正文 ≈ 2 次请求。所以**不能每天全量遍历**，必须分级（热区/全量）。
   > 我一开始以为"只列目录不抓正文就不耗配额"，是错的——实测列目录同样返回"资料获取次数已达上限"。
3. **两类取不到正文**：PDF/Word 是二进制；部分文件报 `not author`（无权限）。别在这上面耗配额。
4. **两套文档都会自称 E1-Ex**——跨文档复用引擎编号前，先查有没有撞车。撞了就加前缀（本次用 OE = Organization Engine）。

## 六、已实现：定期自动同步（智能体跟着组织长）

悟空追加的问题："味藏现在每天都会更新资料，能不能定期拉新资料、自动迭代智能体？"

**能，已经做完了。** 而且这恰恰是 AI原生组织该有的样子——**组织每天长出新资料，智能体就该每天跟着长**。

### 6.1 但配额决定了必须分级（不能每天全量）

实测纠正：**列目录也耗配额**。全量遍历 322 个文件夹 ≈ 320+ 次 API 请求，一天光"看看有没有新增"就花掉大半个配额。所以：

| 级别 | 频率 | 扫描范围 | 抓取上限 | 请求量 |
|---|---|---|---|---|
| **hot 热区** | **每日 08:30** | 11 个高频更新域的顶层 + 直接子文件夹（**62 个**） | ≤8 份 | ~70 次 |
| **full 全量** | **每周日 21:00** | 全部 322 个文件夹 | ≤40 份 | ~400 次 |

### 6.2 同步器 `Claw/_ima_wz_sync.py`

流程：**扫目录 → 与基线 diff 出新资料 → 骨架级优先排序 → 抓正文 → 入库 → 更新基线 → 出同步报告**

| 机制 | 说明 |
|---|---|
| **基线 diff** | `_baseline.json`（322文件夹/4916文件快照）+ `_sync_state.json`（已抓 media_id），只抓**新增**，绝不重复抓 |
| **骨架级优先** | 标题命中「顶层设计/总纲/架构/权重/制度/7S/SKILL」→ 优先抓 + 单独告警。同样是 8 个配额，抓"权重制度"比抓第 9 份周报值钱得多 |
| **二进制跳过** | PDF/Word/PPT/Excel 抓不到文本，直接跳过，不浪费配额 |
| **配额保护** | 请求数硬上限；遇到 `220021` 立即停止，不重试不空转，报告里写明"明日续跑" |
| **入库落点** | `skills/味藏总智能体/references/大库资料/_增量/<日期>/` |

### 6.3 一条铁律：不自动改 SKILL

检测到**骨架级新资料**（顶层设计/总纲/架构/权重/制度）时，同步器只做两件事：**搬进来 + 提示你**。

**绝不自动修改任何 SKILL 文件。**

> 理由：味藏的口径就是组织宪法。新资料可能推翻现有口径，但**推翻与否必须人说了算**——这正是"方向盘永远在人手里"的工程落地。确认后再改，且按老规矩：新旧口径写对照表，旧的标"作废"而非删除。
