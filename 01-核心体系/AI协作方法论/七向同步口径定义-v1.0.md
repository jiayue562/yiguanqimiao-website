## 〇、定题：真问题不是"六改成七"，是本机有两套都叫「六向同步」的东西

改口径前先做了一次全机扫描，扫出一个必须先解决的事实：

**本机存在两套互不相干的"六向"，共用同一个名字。**

| | 口径 A · 内容分发六向 | 口径 B · AI印记六节点 |
|---|---|---|
| 问的问题 | 一份定稿要落到哪几个地方 | 一条知识从产生到被 AI 爬取经过几个节点 |
| 成员 | 桌面双盘／Obsidian／LLM Wiki／IMA／网站／公众号 | WorkBuddy／Obsidian／IMA／GitHub／Cloudflare／pages.dev |
| 载体 | `MEMORY.md` 关键路径、`六向同步批次落位` SKILL | `AI印记系统` SKILL、巡检自动化 `workbuddy-obsidian` |
| 性质 | **落点**（东西放哪儿） | **链路**（东西怎么流到 AI 面前） |

**如果不先把这两个分开命名，"升级七向"会一次性改错两边。**

- 得到大脑是**落点** → 加在口径 A → 六向变**七向**
- 得到大脑不产生网页、不被 AI 爬虫索引 → **不是**印记链路节点 → 口径 B **保持六节点不变**

**初判一句话**：七向＝分发口径加一个落点；印记口径原地不动，且从此改称「六节点巡检」，不再叫"六向"，两套名字彻底分家。

## 一、七向清单（按数据敏感度递增排列）

| # | 向 | 落点 | 敏感度 | 准入 |
|---|---|---|---|---|
| ① | 桌面 | D 主 + C 镜像双盘 | 本地·最低 | 全量 |
| ② | Obsidian | `以观其妙书院\` | 本地 | 全量 |
| ③ | LLM Wiki | `wiki-knowledge\wiki\` | 本地 | 全量 |
| ④ | IMA | 以观其妙书院库 | 云端·自有 | 全量 |
| ⑤ | **得到大脑** ★新增 | 指定 `topic_id`（知识库） | **云端·第三方 SaaS** | **仅成品** |
| ⑥ | 网站 | `yiguanqimiao-website` | 公开 | 成品·去敏 |
| ⑦ | 公众号 | wenyan 草稿箱 | 公开·署人名 | 成品·去敏·最高审慎 |

**排序依据**：从本地到云端、从自有到第三方、从私域到公开。第 ⑤ 位卡在"自有云端"与"公开"之间——它托管在外部厂商，敏感度高于 IMA，低于自己的网站。

## 二、第七向（得到大脑）准入规则

### 2.1 通道事实（已核实，非推测）

| 能力 | MCP 工具 | 说明 |
|---|---|---|
| 写入 | `save_note` | 传 `topic_id` 指定知识库；`note_type: "plain_text"`，正文放 `content` |
| 更新 | `update_note` | 只传要改的字段，其余保持不变 |
| 删除 | `delete_note` | 移入回收站，须先确认目标 |
| 分享 | `share_note` | 生成公开链接，**未明确要求时不调用** |
| 配额 | read/write/write_note/ai_chat 四类分别计数 | 写入**消耗配额**，不是免费的 |

### 2.2 三条准入（硬）

1. **只进成品，不进素材。**
   第七向收的是定稿文档。草稿、会议录音转写、AI"发芽"输出一律不进。
   > 理由：10-22 首同步时勘察过 160 条原始笔记——里面混着 `I have gathered sufficient material. Now let me compose the sprout output.` 这类英文思维痕迹和第二人称对话体。把这类东西推进去，等于把对话记录当知识资产入库。本地存了还能改，推进第三方 SaaS 再想清理，成本就不是一个量级。

2. **味藏内部资料不进第七向。**
   人名、薪酬、业绩数字、权重——不进。
   > 理由：既有纪律是"味藏内部资料不上网站与公众号"。得到大脑是第三方托管的云端库，敏感度**高于**本地三向，只比公开端低一档。把它当本地盘用是错的。

3. **版权与敏感单品不进。**
   第三方付费课程的重构稿、政治敏感题材——不进。

### 2.3 反向动作不占「向」

从得到大脑**往外拉**（读取笔记、回补本地）是**源动作**，走既有「取阅决策树」，**不占第七向编号**。

> 否则"七向"里会同时装着一个推、一个拉，方向相反，口径必乱。推＝同步，拉＝取阅，两件事。

## 三、口径 B 澄清：AI印记保持六节点

`AI印记系统` SKILL 与巡检自动化 `workbuddy-obsidian` 里的"六向"是**链路节点**，不是落点：

```
WorkBuddy ──→ Obsidian ──→ IMA ──→ GitHub ──→ Cloudflare ──→ pages.dev
(知识产生)    (本地知识库)  (云端)  (代码仓库)  (CDN)        (AI索引入口)
```

得到大脑不在这条链上——它不产出可被爬虫索引的网页，不贡献 AI 印记。**六节点维持不变，且今后表述统一为「六节点巡检」，不再称"六向"。**

## 四、顺带修正：IMA 节点口径（28 天误判）

同日巡检口径修正，一并写入本定义以免再次漂移：

- **旧**：IMA 阻塞（skill 级鉴权失效 `200002`，需重新授权）
- **新**：**IMA 参数约束——`limit` 上限 20**。传 50 返回 `code=51`，被误读成鉴权失败。

2026-10-22 以 `limit=20` 复测：`code=0 success`，列出 12 个知识库。**IMA 从未阻塞。**

> 代价记录：这条 10-09 就提出过，搁置 13 天，而"阻塞"已累计 28 天。省一次配额的代价是多挂 28 天。

## 六、待悟空确认

1. **第七向默认开还是默认关？** 建议**默认关**——每份定稿是否推进得到大脑，逐次问。理由：它是唯一一个消耗外部配额、且托管在第三方的向，自动化推送一旦开错，撤回要进回收站捞。
2. **推进去用哪个库？** 8 个库里选：建议成果类进「象思维与思维模型」（44 条，已是最大理论库），理论解析类进「五行人格学」。或新建一个「以观其妙书院·成品」库单放同步件，与原始笔记流隔开。
3. **`六向同步批次落位` 这个 SKILL 要不要正式改名？** 现按"保留旧名 + 内加声明"处理，避免悬空引用；若你要彻底改名，需先跑未覆盖校验再动目录。
